# Дорожная карта развития системы

> Этот документ является roadmap проекта и журналом этапов развития.
> Для первого входа в проект, локального запуска и повседневной разработки используйте `README.md` и `docs/onboarding.md`, а не этот файл как operational entrypoint.

## Организация работ

Этот `plan.md` фиксирует поэтапное развитие продукта на уровне значимых инкрементов, без декомпозиции на мелкие технические задачи. Для каждого этапа план задает цель, ценность, статус и критерии завершения, а детальная реализация переносится в соответствующий tasklist. Принцип планирования: один этап дорожной карты соответствует одному основному `tasklist` в `docs/tasks/`.

## Ключевые особенности плана

- **Backend-first как единое ядро.** Все клиентские каналы (Telegram-слой и `frontend/`) развиваются как слои над общей backend-логикой, чтобы не дублировать доменные правила.
- **Инкрементная поставка ценности.** Каждый этап дает завершенный результат для пользователя или команды, который можно проверить по DoD.
- **Управляемая параллельность.** Параллельная работа допускается только между слабо связанными этапами и при фиксированных контрактах взаимодействия.

## Легенда статусов

- 📋 Planned — запланирован
- 🚧 In Progress — в работе
- ✅ Done — завершён

## Итерации

### Итерация 0: Backend bootstrap

Цель: зафиксировать технологическую и архитектурную основу backend до проектирования контрактов и каркаса сервиса.

⚡ Параллельность: служит подготовительным слоем для Итерации 1 и не должна смешиваться с реализацией endpoint'ов или рефакторингом клиентов.

Критерии завершения (DoD):
- выбран backend-стек и закреплен в отдельном ADR;
- введены conventions для backend-first структуры и инженерных команд;
- backend-tasklist явно связывает задачу 01 с bootstrap-итерацией.

Связь с tasklist: [docs/tasks/tasklist-backend.md](tasks/tasklist-backend.md)

Полезный результат: команда получает единую технологическую базу и границы ответственности перед началом `Backend foundation`.

Артефакты:
- `docs/tasks/impl/backend/iteration-0-backend-bootstrap/plan.md`
- `docs/tasks/impl/backend/iteration-0-backend-bootstrap/summary.md`
- `docs/adr/adr-002-backend-stack.md`
- `.cursor/rules/conventions.mdc`

### Итерация 1: Backend foundation

Цель: сформировать backend как единое ядро бизнес-логики системы мониторинга.

⚡ Параллельность: можно частично вести параллельно с Итерацией 2 по UI/диалогам бота, если API-контракты и ошибки зафиксированы заранее.

Критерии завершения (DoD):
- зафиксированы ключевые архитектурные решения backend и границы ответственности с клиентами;
- описаны и согласованы базовые API-контракты для сценариев из `vision.md`;
- backend готов как единая точка входа для клиентов и интеграций.

Связь с tasklist: [docs/tasks/tasklist-backend.md](tasks/tasklist-backend.md)

Полезный результат: команда получает стабильное ядро, на которое можно опирать развитие всех клиентов.

Артефакты:
- `docs/tasks/tasklist-backend.md`
- `docs/adr/` (новые или обновленные ADR по backend-решениям)
- `backend/docs/openapi.yaml`
- `backend/docs/api-contracts.md`
- `README.md`
- `.env.example`
- `docs/tasks/impl/backend/iteration-1-backend-foundation/tasks/task-06-backend-documentation/plan.md`
- `docs/tasks/impl/backend/iteration-1-backend-foundation/tasks/task-06-backend-documentation/summary.md`
- `docs/tasks/task-08-quality-and-docs-sync/plan.md`
- `docs/tasks/task-08-quality-and-docs-sync/summary.md`

### Итерация 2: Telegram MVP client

Цель: обеспечить пользовательские сценарии MVP в Telegram через backend API.

⚡ Параллельность: может выполняться параллельно с Итерацией 3, так как оба клиента используют общий backend и разделяют контрактный слой.

Критерии завершения (DoD):
- бот закрывает ключевые MVP-сценарии быстрых запросов по состоянию оборудования;
- прямая бизнес-логика в боте минимизирована, обмен идет через backend API;
- ответы формируются в понятном прикладном языке.

Связь с tasklist: [docs/tasks/tasklist-backend.md](tasks/tasklist-backend.md) до выделения отдельного `tasklist-bot.md`.

Полезный результат: пользователи получают первый рабочий канал мониторинга с быстрыми ответами.

Артефакты:
- `docs/tasks/tasklist-backend.md`
- `docs/tasks/task-07-bot-backend-client/plan.md`
- `docs/tasks/task-07-bot-backend-client/summary.md`
- обновления соглашений взаимодействия bot-backend в `docs/integrations.md`

### Итерация 3: Frontend unified client

Цель: запустить единый frontend-клиент для ролей админа и пользователя.

⚡ Параллельность: параллельно с Итерацией 2 на общей API-базе; итоговая приемка зависит от готовности backend-контрактов из Итерации 1.

Критерии завершения (DoD):
- реализован единый web-интерфейс для обзора состояния и навигации по зонам мониторинга;
- обеспечены базовые сценарии для обеих ролей из `vision.md`;
- frontend-клиент работает через тот же backend API без обходных путей.

Связь с tasklist: до выделения отдельного tasklist опираться на документы в `docs/tasks/impl/frontend/`.

Полезный результат: команда получает централизованный визуальный канал мониторинга для регулярной работы.

Артефакты:
- `docs/tasks/impl/frontend/`
- обновления UI/роль-сценариев в проектной документации (по факту реализации)

### Итерация 4: Monitoring and LLM integrations

Цель: подключить внешние источники мониторинга и контур LLM-интерпретации в едином backend-потоке.

⚡ Параллельность: ограниченно параллельна с Итерацией 5 по части наблюдаемости, если интерфейсы интеграций уже стабилизированы.

Критерии завершения (DoD):
- backend принимает данные от внешних источников мониторинга по согласованным контрактам;
- интерпретация состояния через LLM встроена в целевой пользовательский поток;
- определено fallback-поведение при недоступности внешних интеграций.

Связь с tasklist: tasklist будет выделен отдельно по мере стабилизации интеграционного контура.

Полезный результат: система показывает не только данные, но и понятную интерпретацию состояния для принятия решений.

Артефакты:
- обновления `docs/integrations.md`

### Итерация 5: Platform readiness

Цель: обеспечить устойчивую эксплуатацию системы и управляемое развитие контрактов.

⚡ Параллельность: может идти параллельно с финализацией Итерации 4 по части процессов качества и документации.

Критерии завершения (DoD):
- зафиксированы единые соглашения по форматам запросов, кодам ошибок и версионированию API;
- настроены базовые инженерные практики: тесты, линтеры, минимальная наблюдаемость, единые сценарии локального запуска;
- `vision.md`, `data-model.md`, `integrations.md` актуализированы по фактической реализации.

Связь с tasklist: [docs/tasks/tasklist-devops.md](tasks/tasklist-devops.md)

Полезный результат: продукт готов к предсказуемой поддержке и масштабированию без потери целостности архитектуры.

Артефакты:
- `docs/tasks/tasklist-devops.md`
- обновления `docs/vision.md`, `docs/data-model.md`, `docs/integrations.md`
