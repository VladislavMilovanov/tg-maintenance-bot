# ADR-002: Backend stack и границы backend-first ядра

- **Статус:** Accepted
- **Дата:** 2026-03-30
- **Контекст:** запуск backend bootstrap перед `Backend foundation`

---

## Контекст

Проект уже содержит Telegram-бота на Python 3.12, но backend как отдельное ядро системы еще не реализован. При этом `vision.md` уже фиксирует backend-first модель: бизнес-логика, анализ состояния оборудования, фиксация результатов и интеграции должны находиться в backend, а bot и web выступают клиентами.

До начала проектирования API и каркаса backend нужно закрепить:

- runtime и основной framework для HTTP API;
- базовые инженерные инструменты;
- правила конфигурации через env;
- границы ответственности между backend и клиентами.

Без этого следующие задачи рискуют разойтись по стеку, структуре каталогов и способу запуска сервиса.

## Рассмотренные альтернативы

### 1) FastAPI + uv + pydantic-settings + pytest + ruff

**Плюсы:**
- полностью совместимо с текущим Python 3.12 проектом;
- дает быстрый старт для HTTP API, OpenAPI и валидации схем;
- хорошо сочетается с async стеком и текущим Python-ботом;
- `uv` упрощает локальный workflow и управление зависимостями;
- `pytest` и `httpx`/`TestClient` закрывают базовый слой API-тестов без лишней инфраструктуры.

**Минусы:**
- добавляет второй исполняемый контур в репозиторий еще до реализации функциональности;
- потребует дисциплины в разделении bot-кода и backend-кода.

### 2) Flask / Django как HTTP-основа

**Плюсы:**
- зрелые и известные инструменты;
- широкий набор расширений.

**Минусы:**
- Flask требует больше ручных соглашений для схем, OpenAPI и валидации;
- Django избыточен для целевого MVP и сильнее навязывает структуру, чем требуется на bootstrap-этапе;
- меньше пользы относительно FastAPI для контрактно-ориентированного API-first сценария.

### 3) Сохранить backend внутри Telegram-бота без отдельного сервиса

**Плюсы:**
- минимальные стартовые изменения;
- проще локальный запуск на короткой дистанции.

**Минусы:**
- противоречит `vision.md` и backend-first принципу;
- закрепляет дублирование логики для будущего web-клиента;
- усложняет масштабирование интеграций, тестов и контрактов.

## Решение

Выбираем для backend bootstrap следующий базовый стек и правила:

- **Python 3.12+** как единый runtime проекта;
- **FastAPI** как основной framework для backend HTTP API;
- **uv** как стандартный инструмент для установки зависимостей и запуска Python-команд;
- **pydantic-settings** для конфигурации через переменные окружения;
- **pytest** вместе с **httpx** и/или **FastAPI TestClient** для backend API-тестов;
- **ruff** как единый линтер и formatter;
- **make** как верхнеуровневая точка входа для стандартных команд разработки.

Границы ответственности фиксируем так:

- backend является единственным местом доменной логики, интеграций и правил интерпретации состояния;
- Telegram-бот и будущий web являются thin clients и обращаются к backend по контрактам;
- прямой вызов LLM или доменных сервисов из клиентов допускается только как временное текущее состояние до миграции на backend API, но не как целевая архитектура.

## Обоснование

- Решение следует уже принятому backend-first направлению из `vision.md`.
- Стек минимально расширяет текущий Python-проект и не требует смены runtime.
- FastAPI естественно поддерживает OpenAPI и контрактно-ориентированную разработку, что критично для следующих задач 02 и 06.
- Отдельная фиксация thin-clients границы снижает риск повторного размещения бизнес-логики в Telegram-боте или web-клиенте.

## Последствия

### Позитивные

- у команды появляется единая база для проектирования API и каркаса backend;
- naming и будущие команды backend фиксируются до реализации;
- bot и web получают четкие архитектурные границы.

### Негативные / компромиссы

- часть текущей логики бота придется вынести в backend на следующих этапах;
- в репозитории временно будет сосуществовать текущий bot-first код и target backend-first документация;
- команды `make run-backend`, `make test-backend`, `make lint-backend` будут сначала нормативными, а не реализованными до задачи 03.

## План пересмотра

ADR пересматривается, если:

- backend перестает быть единым ядром системы;
- для API выбирается другой framework;
- появляются организационные ограничения, несовместимые с `uv` или `make` как базовыми инструментами.
