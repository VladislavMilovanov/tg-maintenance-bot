# ADR-001: Выбор СУБД для системы мониторинга оборудования

- **Статус:** Accepted
- **Дата:** 2026-03-26
- **Контекст:** MVP и дальнейшее развитие multi-component системы (`bot`, `backend`, `web`)

---

## Контекст

Система включает несколько клиентов и единое серверное ядро, где централизована логика мониторинга, фиксации состояния и аналитики.  
Нужна СУБД, которая:

- хорошо поддерживает реляционные данные и связи;
- подходит для истории состояний и фиксации результатов;
- масштабируется при росте количества сервисов и нагрузки;
- остаётся простой для старта MVP.

---

## Рассмотренные альтернативы

### 1) PostgreSQL

**Плюсы:**
- сильная поддержка реляционной модели и целостности данных;
- зрелая экосистема и стабильность в production;
- удобное расширение (индексы, JSON-поля, аналитические запросы);
- хорошо подходит как единая транзакционная база для нескольких сервисов.

**Минусы:**
- требует больше операционной дисциплины, чем файловые решения;
- для команды без опыта может быть чуть выше порог входа, чем у SQLite.

### 2) MySQL

**Плюсы:**
- зрелая и распространённая реляционная СУБД;
- подходит для типовых транзакционных сценариев.

**Минусы:**
- меньше гибкости для части аналитических и гибридных сценариев;
- в данном проекте не даёт явных преимуществ относительно PostgreSQL.

### 3) MongoDB

**Плюсы:**
- гибкая схема, быстрый старт для документов.

**Минусы:**
- модель проекта по сути реляционная (пользователи, роли, оборудование, датчики, история);
- сложнее поддерживать строгую целостность связей;
- повышается риск усложнения при доменной эволюции.

### 4) SQLite

**Плюсы:**
- очень простой запуск, минимальные издержки на MVP.

**Минусы:**
- ограничена для multi-service сценариев и роста нагрузки;
- нецелевой вариант для production-этапа системы сопровождения мониторинга.

---

## Решение

Выбираем **PostgreSQL** как основную СУБД проекта, начиная с MVP.

---

## Обоснование

- Лучшая совместимость с текущей доменной моделью и её связями.
- Поддерживает как стартовый объём MVP, так и дальнейший рост системы.
- Даёт единый устойчивый базис для backend и будущей сервисной декомпозиции.
- Снижает риск миграции СУБД на следующем этапе развития продукта.

---

## Последствия

### Позитивные
- единая реляционная модель для пользователей, ролей, оборудования, датчиков и истории;
- прозрачные правила целостности и консистентности;
- прогнозируемое масштабирование без смены базовой СУБД.

### Негативные / компромиссы
- инфраструктура сложнее, чем у локальных файловых решений;
- потребуется дисциплина в миграциях и эксплуатации.

---

## План пересмотра

Пересмотр ADR требуется, если:

- возникают нетипичные требования по нагрузке или хранению временных рядов;
- появляется необходимость выделения специализированного хранилища под отдельный профиль данных;
- меняется архитектурная стратегия по границам сервисов.
