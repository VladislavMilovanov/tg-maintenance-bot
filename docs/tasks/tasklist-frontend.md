# Frontend Tasklist

## Обзор

Список задач по разработке web-клиента системы мониторинга оборудования. Стек: Next.js (App Router) + React + TypeScript + shadcn/ui + Tailwind CSS + pnpm. Web-приложение является тонким клиентом поверх backend API и предоставляет три основных экрана (площадка → оборудование → узел) + глобальный AI-чат.

## Итерация 00: Требования к UI и API-контракты для frontend ✅

### Цель

Зафиксировать функциональные требования к экранам и спроектировать API-контракты для frontend.

### Состав работ

- [x] Сформировать функциональные требования к четырём зонам интерфейса:
  - **Экран 1 — Панель обзора площадки (Plant Overview Dashboard):**
    - Индекс состояния завода (green/yellow/red) — агрегированный worst-status по всему оборудованию
    - График состояния оборудования по дням (14 дней) — line/bar chart
    - Лента изменений состояния оборудования (state change feed)
    - Лента действий с оборудованием (action feed — кликабельно, ведёт к отчётам и деталям)
    - Сводка по количеству оборудования в каждом статусе (normal/warning/critical/unknown)
    - Топ проблемных единиц оборудования (worst performers)
    - Цель экрана: любой посетитель портала сразу получает ответ — что происходит, всё ли работает
  - **Экран 2 — Панель обзора оборудования (Equipment Detail Dashboard):**
    - Индекс состояния оборудования (green/yellow/red)
    - Переключатель: таблица общих данных по машине / ключевой параметр (индивидуальный для каждой единицы)
    - Прогресс-бар по техническому обслуживанию
    - Топ-3 самых важных узла (sensor groups), на которые надо обращать внимание
    - История состояний и действий по данному оборудованию
  - **Экран 3 — Панель обзора узла (Sensor Group Detail):**
    - Индекс состояния узла (green/yellow/red)
    - Фото узла
    - Основные мониторируемые характеристики
    - AI-диагностика словами — интерпретация текущего состояния от LLM
    - Если состояние yellow/red — объяснение причин и рекомендации по исправлению для предотвращения остановки производства
  - **Глобальный чат** — плавающая кнопка на всех экранах: пользователь получает ответ от AI о состоянии завода/оборудования/узла или задаёт уточняющий вопрос
- [x] Зафиксировать правило агрегации статусов: worst-status-wins снизу вверх (узел → оборудование → площадка)
- [x] Зафиксировать общий стиль UI: светлая/тёмная тема, dev-стиль (референс: https://www.tbench.ai/)
- [x] Зафиксировать временную схему входа: ввод Telegram username (без сложной авторизации), с планом миграции на логин/пароль
- [x] Спроектировать API-контракты для всех экранов (новые endpoint'ы для frontend)
- [x] Актуализировать `backend/docs/api-contracts.md` и `backend/docs/openapi.yaml`

### Definition of Done

**DoD — самопроверка агента:**
- [x] Функциональные требования зафиксированы для всех трёх экранов и глобального чата
- [x] Правило агрегации статусов описано явно
- [x] Стиль UI и схема входа задокументированы
- [x] Все новые endpoint'ы описаны в `api-contracts.md` и `openapi.yaml`
- [x] Документы сохранены по указанным путям артефактов

**DoD — проверка пользователем:**

- [x] Открыть `backend/docs/openapi.yaml` — убедиться, что схемы соответствуют контрактам
