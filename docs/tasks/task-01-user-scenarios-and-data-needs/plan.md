# Задача 01: Пользовательские сценарии и требования к данным

## Цель

Зафиксировать базовые пользовательские сценарии и data requirements для ролей `клиент/инженер` и `админ`, чтобы команда могла обсуждать backend, data layer и будущий web без повторного проектирования доменной модели.

## Контекст

- `docs/idea.md` и `docs/vision.md` задают продуктовые границы системы мониторинга оборудования.
- MVP backend уже имеет контракты для assistant flow и ручной фиксации состояния.
- Для следующих задач data stage нужен единый сценарный артефакт и согласованный набор доменных терминов.

## Решения

- Вынести основной сценарный артефакт в `docs/spec/user-scenarios.md`.
- В продуктовых документах использовать единую операционную роль `клиент/инженер`.
- Развести понятия `current state` и `state record`.
- Зафиксировать как обязательные data requirements: `owner`, `data source`, `review_status`, `reviewed_by`, `reviewed_at`.
- Не расширять текущий wire shape API; синхронизировать только термины и границы.

## Состав работ

- Описать роли и базовые пользовательские потоки.
- Вывести из сценариев обязательные представления данных и минимальные сущности.
- Синхронизировать `docs/vision.md`, `docs/data-model.md` и `backend/docs/api-contracts.md`.
- Обновить `docs/tasks/tasklist-database.md` ссылками на реальные артефакты задачи.

## Артефакты

- `docs/spec/user-scenarios.md`
- `docs/vision.md`
- `docs/data-model.md`
- `backend/docs/api-contracts.md`
- `docs/tasks/task-01-user-scenarios-and-data-needs/summary.md`

## Definition of Done

- Есть единый сценарный документ для ролей `клиент/инженер` и `админ`.
- Термины и обязательные представления данных согласованы между scenario-doc, vision, data model и API contracts.
- Документация позволяет проектировать data layer и будущий web без обращения к коду.
