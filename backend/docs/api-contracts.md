# API Contracts: MVP Scenarios

Этот документ кратко поясняет контракты из `backend/docs/openapi.yaml`. Источником истины для DTO, обязательных полей и кодов ошибок остаётся OpenAPI-спека.

## Сценарий 1: Вопрос ассистенту

- Endpoint: `POST /api/v1/assistant/messages`
- Клиент передаёт канал, внешнего пользователя, текст сообщения и опциональный контекст диалога/оборудования.
- Backend отвечает текстом ассистента и возвращает `conversation_id`, который клиент может использовать в последующих запросах.
- Если `conversation_id` не передан, неизвестен или уже истёк, backend начинает новый диалог и всё равно возвращает `200` с новым идентификатором.
- Поле `meta.fallback_used` показывает, что backend не смог получить штатную интерпретацию, но всё ещё смог вернуть деградированный ответ.
- `503` используется только если backend не смог вернуть даже fallback-ответ для пользователя.

## Сценарий 2: Фиксация состояния оборудования

- Endpoint: `POST /api/v1/equipment-state-records`
- Клиент передаёт идентификатор оборудования, итоговый статус, комментарий, время наблюдения, канал и автора фиксации.
- Для безопасных ретраев клиент может передать `idempotency_key`.
- Контракт MVP не включает сенсорные наблюдения, вложения, workflow согласования и review-поля.
- Backend возвращает созданную запись в нормализованной форме с `record_id` и `created_at`.
- `409` используется только для конфликта по уже использованному `idempotency_key` с другим payload; без ключа каждый успешный запрос считается новой записью.

## Общие договорённости

- Версия API начинается с `/api/v1`.
- И Telegram-бот, и будущий web-клиент используют одинаковые DTO и один error-shape.
- В assistant flow вызов LLM выполняется только backend-ом.
- `400` зарезервирован под malformed HTTP/body ошибки, а `422` под ошибки контрактной и бизнес-валидации после успешного парсинга запроса.
- Детали хранения истории диалога и идемпотентности фиксации отложены до задач реализации.

## Operational endpoints

- `GET /health` используется как liveness-check и не зависит от БД.
- `GET /ready` используется как readiness-check и возвращает success только при доступном PostgreSQL.
